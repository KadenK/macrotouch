## Result: 2 intended changes, 1 regression found and fixed, everything else identical

### Intended changes

**SY-06 — concurrent edits.** The point of the ticket.

```
master:   A=true  B=false     one client's macro lost entirely
MAC-40:   A=true  B=true      both survive
```

Two clients upserting different macros now both land, because each sends a command naming its own
macro instead of the whole state map. Checklist item updated.

**SY-07 — malformed message.** The recorded observables all still hold: socket stays open,
`Invalid websocket message` logged, other clients unaffected. New behavior is additive — the
offending client now also receives `{ type: 'error', error: { code: 'invalid-message' } }`.
On master it received nothing. Checklist item updated.

### Regression found and fixed during the run

**ST-02 — `settings` missing from a fresh `state.json`.**

First run after the migration produced `top-level keys: macros,screens` where the baseline had
`macros,screens,settings`. Cause: on master every edit re-sent the whole state, so the client's
`DEFAULT_SETTINGS` were written to disk implicitly. With granular commands, `update-settings`
only fires when settings actually change, so a fresh file never got the key.

Fixed by moving the defaults to `createDefaultSettings()` in `types/state.ts` and seeding them in
the master's `emptyState()`. The master owns the state, so it should own its defaults rather than
inheriting them from whichever client happened to connect first. Re-verified:
`top-level keys: macros,screens,settings`.

### SC-06 — same end state, earlier timing

Worth recording because the plan flagged it as risk #1.

```
                        master                          MAC-40
after shrink to 3 cols  row0 len=6, stale id on disk    row0 len=3, clamped on disk
UI                      renders 3 cells                 renders 3 cells
after reload + 1 edit   placed=false, orphaned          placed=false, orphaned
```

The quirk itself is preserved exactly — the placement is dropped and the macro record is left
orphaned in `macros`, unrecoverable by growing the grid back. What changed is *when* it is
persisted. On master the clamp ran only on the client, on receive, so `state.json` kept a stale
6-column row until some later edit happened to push the normalized state back; disk and UI
disagreed in the meantime. Normalization now runs in the master's `applyCommand`, so disk and UI
agree immediately.

This is a consequence of moving the clamp server-side, which was required: under `state-patch`
the client applies entities directly and the receive-time clamp no longer runs on edits. Leaving
it client-only would have lost the quirk entirely.
