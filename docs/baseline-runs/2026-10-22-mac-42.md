## Baseline: `dist` succeeds, but ships the whole build toolchain

`npm run dist` on `master` @ `7de0461` exits 0 and produces a working DMG, so the ticket's premise
("changing startup without packaging would leave `npm run dist` broken") did not hold — it was
already building. It was, however, building the wrong thing.

```
DMG                       156 MB
app/node_modules          195 MB, 463 packages (nuxt, vue, vite, esbuild, …)
app/images                missing
```

Two defects:

**1. The build toolchain was shipped as a runtime dependency.** `nuxt`, `vue`, `vue-router`,
`@pinia/nuxt`, `@nuxt/icon`, the `@iconify-json/*` packs and `qrcode` were all in `dependencies`.
electron-builder copies production dependencies into the app, so the packaged artifact carried the
entire build toolchain. None of it is reachable at runtime: the web apps are prerendered into
`.output/public` by vite, and the only Node processes are the Electron main process (built-ins
only) and the esbuild-bundled master, whose sole externals are `ws` and `node-notifier`.

It also produced a build error, logged but non-fatal:

```
• preparing  moduleName=@parcel/watcher arch=arm64
⨯ Attempting to build a module with a space in the path
```

`@parcel/watcher` is a native transitive dependency of `nuxt`. Because `nuxt` was a production
dependency, `@electron/rebuild` tried to rebuild it for Electron, and node-gyp cannot build from a
path containing a space — which this checkout has (`/Users/.../School Projects/macrotouch`). The
error is incidental to this machine, but the rebuild attempt should never have happened at all.

**2. `images/` was not packaged.** `electron/main.cjs` reads `images/macrotouch-logo.png` at
startup, but the `files` list did not include it. `nativeImage.createFromPath` returns an empty
image for a missing path rather than throwing, so the packaged app ran with a blank dock and
window icon and logged nothing.

## Changes

- `dependencies` reduced to `node-notifier` and `ws` — the master bundle's two esbuild externals.
  Everything else moved to `devDependencies`. CI installs with `npm ci --ignore-scripts`, which
  keeps dev dependencies, so nothing there changes.
- `images/**/*` added to `build.files`.
- Removed the dead `macro:trigger` IPC handler and the `app:ready` / `app:update` / `macro:trigger`
  preload bridge. Nothing in `app/` used any of them. `dialog:selectExecutable` stays — it is live,
  used by `app/components/input/executablePathInput.vue`.

```
app/images                present  (was missing)

```

## Rebased onto MAC-41

This ran first against `master`, then was re-based onto
[MAC-41](https://linear.app/macrotouch/issue/MAC-41/split-actions-into-a-separate-action-server-process)
once that branch was finished but unmerged. MAC-41 already carries `build:action`, `start:action`,
`dist-action/**/*` in `files` and the `.gitignore` entry, so the packaging work this ticket was
waiting on arrived with it. The `files` list merged cleanly: `images/**/*` here, `dist-action/**/*`
there.

Its launcher resolves `../dist-action/index.mjs` relative to the master bundle, which lands on
`Resources/app/dist-action/index.mjs` in the packaged app — no path rewriting needed. The action
server is spawned with `process.execPath`, which for the packaged master is the Electron binary,
and it works because `ELECTRON_RUN_AS_NODE=1` is inherited from the environment Electron gave the
master. That inheritance is load-bearing and invisible; worth setting explicitly in the launcher
if anything about the spawn chain changes.

## Fixed here: `npm run dev` ran a stale action server

The launcher picked its entry as `existsSync(dist-action/index.mjs) ? bundle : source`. In a
checkout, that bundle exists as soon as anyone has run `npm run build` or `npm run dist` once —
so `npm run dev` ran the **built** action server instead of the TypeScript source, and edits under
`action-server/` silently stopped taking effect. Confirmed by process inspection: with a bundle
present, dev was running `node .../dist-action/index.mjs`, not the source.

Nothing in dev watches `action-server/` either: `tsx watch` only follows `master-server/index.ts`
and its imports, and the action server is no longer one of them.

Fix: the launcher honours `MACROTOUCH_ACTION_ENTRY`, and `dev` / `dev:electron` set it to
`action-server/index.ts`. Dev now runs `node --import tsx .../action-server/index.ts` with a bundle
present. The packaged app sets no override, so it still takes the bundle — re-verified on a rebuild
after the change.

Note this still means an action-server edit needs a dev restart to take effect. It is no longer
*silently* stale, which was the actual bug, but hot reload for that process is not wired up.

## Role routing changed: PA-04, PA-08 and PA-09 rewritten

MAC-39 replaced server-side role routing with URL-based role routing. `server/middleware/
ipRedirect.ts` — which 302'd LAN clients to `/screen` and localhost to `/home` — was removed in
`6a8de6b`, and two client-side changes landed in the same commit to take its place:

- `app/pages/index.vue` was added: `/` is a "What is this device?" chooser offering **Editor** and
  **Controller**, instead of guessing from the caller's IP.
- `getIPAddresses.ts` builds connect URLs as `http://<ip>:4321/screen`, so the QR and the typed
  URL land a phone directly on the runtime.

A device is now routed by the URL it was handed rather than by where it connected from. Measured
against the packaged app:

```
localhost  /          200   chooser page
LAN        /          200   chooser page
LAN        /home      200   editor
LAN        /settings  200   settings
LAN        /connect   200   connect
LAN        /screen    200   runtime   <- what the QR and listed URL point at
```

Three checklist items described the old mechanism and have been rewritten against the new one,
each keeping its ID with the old wording struck through and a pointer to MAC-39, per the
checklist's rule for items that stop applying:

- **PA-04** — the listed URL is `http://<ip>:4321/screen`, not `/`.
- **PA-08** — remote clients land on the runtime because that is what the advertised URL points
  at. The suite asserts a LAN request for `/screen` returns 200, and logs the status of the other
  routes so a future move back to redirects shows up as a diff instead of passing silently.
- **PA-09** — `/` is the chooser; the suite asserts it offers both roles and that each reaches its
  page.

One consequence is worth having on the record even though it is now the intended contract: the
master serves every route to every client, so a remote device that navigates to `/home` or
`/settings` by hand reaches the editor. Nothing enforces the role the URL implies. If that should
ever be enforced, it is a new ticket and PA-08 would be rewritten again.

## Not done, and why

**The action server bundle.** The ticket asks for "the master and action server bundles" in
`files`. Resolved — it came with MAC-41, and this branch is now based on it.
Nothing is outstanding here.

**Enabling asar.** electron-builder warns about `asar: false` on every run, and it is tempting to
treat it as part of "update packaging". It is not a small change here, and it should be its own
ticket:

- The master runs as a plain Node process (`ELECTRON_RUN_AS_NODE`), and that mode does not install
  Electron's asar support in `fs`. So the master bundle, everything it reads, and everything it
  resolves must sit outside the archive.
- That means `dist-master`, `.output/public` (served by the master with `fs.createReadStream`),
  and the `ws` / `node-notifier` packages all need `asarUnpack` or `extraResources`.
- The same will apply to `dist-action` and its launcher once MAC-41 lands.

Now that both sidecars exist, one ticket can handle them together with a single convention.

## Worth knowing

**The packaged master's console goes nowhere.** `ensureMaster` spawns it with `stdio: 'ignore'`,
so in the packaged app there is no way to see what the master logs. The checklist leans on the
server console as the observable for ST-05, ST-06, MC-09, RT-03 and AC-09 — all of which are
unobservable in a built app today. Not a regression and not in this ticket's scope, but it is why
the AC-04 check above had to be run against the packaged runtime directly instead of through a
macro trigger.
